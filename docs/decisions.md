# Technical Decision Log

Each decision lists the alternatives considered, the choice, and the reason. Decisions marked ⚠ rest on reasoning that
still needs to be confirmed with the real embedding model on a larger corpus (the commands are in the README).

## D1. Chunking: recursive, structure-aware, 400 characters, 66 overlap, page-bounded
- **Alternatives:** fixed-size character/token windows; sentence-based; semantic chunking (split where embedding similarity drops); whole-page chunks; much larger chunks (1000–1600 chars).
- **Choice:** recursive splitting on paragraph → line → sentence → clause → word boundaries, packed up to 400 chars (~100 tokens) with ~66 chars overlap (1/6 of the size); chunks never cross a page.
- **Why:** policy/FAQ/report text is organised in short sections (300–700 chars). Splitting on natural boundaries keeps a rule and its number together ("25 days of paid annual leave…"), which both retrieval and citations need. Overlap protects facts that straddle a boundary. Page-bounded chunks give exact page citations. Fixed windows cut sentences in half; semantic chunking costs an embedding pass per sentence at ingest and is harder to debug for little gain on structured business documents. 400 chars is far below the embedder's 512-token limit, so nothing is truncated.
- **Evidence (real embeddings, Run 1):** Hit@1 / MRR for 250 / 400 / 600 / 1000 / 1600 chars = 1.00/1.00, 1.00/1.00, 0.93/0.97, 0.80/0.90, 0.80/0.90; Precision@3 0.49 / 0.44 / 0.42 / 0.40 / 0.40. Large chunks mix several topics into one embedding and dilute the match. **I started with 600 on reasoning alone, the sweep showed it was not the best, so the default was changed to 400.** 250 ties 400 but risks separating a fact from its context.
- **Caveat:** 15 answerable queries; short sectioned documents. Re-run `--chunk-sweep` on longer documents before generalising. Run 2 (20 answerable queries incl. paraphrases) repeated the sweep and gave the same ordering: Hit@1 0.95 (250), 0.95 (400), 0.85 (600), 0.80 (1000), 0.80 (1600).

## D2. Embedding model: local `BAAI/bge-small-en-v1.5` (not an API, not a larger model)
- **Alternatives:** `all-MiniLM-L6-v2` (faster, older, 256-token limit); `bge-base/large`, `e5`, `gte` (better quality, 3–10× slower and bigger); hosted embedding APIs (OpenAI, Voyage, Cohere).
- **Constraint:** Anthropic does not provide an embedding model, so embeddings cannot come from Claude. I did not want a second paid API key for an assessment, which favours a local open-source model.
- **Choice:** bge-small-en-v1.5: 384-dim, ~33M parameters, runs on CPU in milliseconds per chunk, 512-token context, designed for retrieval (uses a query instruction prefix, which the code adds). It is a common quality/latency sweet spot for a small corpus.
- **How the decision should be verified:** `python -m evaluation.run_eval --backend sentence-transformers --embedding-model <model> --calibrate` runs the same 20 labelled queries for each candidate and reports Hit@k, MRR, precision and the gate separation. bge-small ran end-to-end on the candidate's machine (Run 1: relevant queries scored 0.67–0.91, off-topic 0.48–0.53, so the scores separate topics well). A head-to-head against MiniLM or a larger model has **not** been run, so the model is a reasoned default, not a measured winner.
- **Fallback:** a hashing bag-of-words embedder exists so tests and CI run offline. It is lexical, not semantic, and is labelled as such everywhere.

## D3. Retrieval: hybrid (dense + BM25 with Reciprocal Rank Fusion), not dense-only
- **Alternatives:** dense only; BM25 only; weighted score fusion; adding a cross-encoder reranker; HyDE / multi-query expansion.
- **Choice:** both retrievers return their top 20; RRF (k=60) fuses by rank.
- **Why:** dense search handles paraphrase ("minimum password length" vs "at least 14 characters"), BM25 handles exact tokens that embeddings blur (product names, numbers, years like "2024"). RRF needs no score normalisation between two incompatible scales. A cross-encoder reranker would likely add accuracy but costs another model download and latency, so it is listed as a future improvement rather than built.
- **Evidence (Run 1, real embeddings):** Hit@1 dense 0.87, BM25 0.93, hybrid 0.93; MRR 0.91 / 0.97 / 0.97. Hybrid beat dense by one query and only *tied* BM25. My first queries reuse the documents' wording, which favours BM25, so Run 2 adds paraphrased queries (q21–q25) to test the case hybrid is meant for. **Run 2 result:** hybrid Hit@1 0.95 / MRR 0.97 / EvidenceRecall 1.00 vs dense 0.90 / 0.94 / 0.97 and BM25 0.90 / 0.93 / 0.95. BM25 missed the paraphrase q22 completely. The margins are one query each, so the evidence is the *pattern* (BM25 fails on paraphrases, hybrid does not), not the decimals.

## D4. Unanswerable questions: a layered defence, not a single threshold
- **Alternatives:** only prompt the LLM to say "I don't know"; only a similarity threshold; LLM-as-judge faithfulness check on every answer.
- **Choice:** (1) cosine **relevance gate** before the LLM (cheap, removes off-topic queries without an LLM call); (2) prompt rule + `answerable` field so the LLM can abstain when passages are only topically related; (3) deterministic **post-verification**: citations must refer to supplied passages, an uncited "answer" is converted into an abstention, numbers must appear in the cited text.
- **Why:** each layer fails differently. Real scores (Run 1) show the gate alone cannot separate "topically related but unanswered" questions: parental leave scores 0.686 and the Orbit-price question 0.746, inside the answerable range 0.673–0.911. Claude refused all 5 unanswerable questions in both runs (5/5), so the LLM and verification layers are required, not optional. Run 2 showed the opposite failure of the verification layer: 3 answerable questions were withheld because Claude gave no citation. The pipeline now retries once or twice with the valid labels before withholding (still refuses if the answer stays uncited).
- **Threshold:** real sweep: 0.50 → 20% of unanswerable rejected, 0.60 → 60%, 0.70 → 80% but only 87% of answerable kept. Default **0.60**: same rejection as 0.65 with a margin below the weakest answerable query. Run 2 (with paraphrase queries) lowered that weakest score to 0.645 (q25) and the tool recommended 0.59; 0.60 is kept because it keeps all 20 answerable queries, with a 0.045 margin. 0.65 would already lose q25. The first automatic recommendation (0.67) sat 0.003 below that query and was rejected as overfit; the tool now recommends "weakest answerable score − 0.05".

## D5. Structured output from Claude: strict tool schema with `tool_choice: auto` (not forced tool use, not free-text JSON)
- **Alternatives:** ask for JSON in text and parse it; force a tool call with `tool_choice: {"type":"tool"}`; the Structured Outputs feature.
- **Finding:** the current Anthropic docs state that Sonnet 5.5 (and Opus 5.5 / Fable / Mythos 5.x) return a 400 for forced tool use. A forced-tool design would simply fail on the model I'm using.
- **Choice:** define a `submit_answer` tool with a strict JSON schema, leave `tool_choice` on auto, instruct the model to call it, re-prompt once if it replies in plain text, and parse JSON from text only as a last resort. The result is validated again with Pydantic (one repair retry), then fails with a clear 502. Optional parameters (`temperature`, `strict`) are dropped automatically if the API *or the installed SDK version* rejects them (a newer SDK refused `temperature` locally on the candidate's machine, which is how this was found), so changing `RAG_LLM_MODEL` does not break the app.

## D6. Duplicates vs conflicts: de-duplicate by content, never by similarity alone
- **Problem:** two versions of a policy differ only by "20 days" vs "25 days". Their embeddings are almost identical, so naive near-duplicate removal would silently delete one version — the worst possible outcome.
- **Choice:** exact duplicates (same normalised text) are merged at both document and chunk level; near-duplicates (cosine ≥ 0.95) are merged **only if their numeric tokens are identical**. Chunks from different documents that are similar (≥ 0.75) but have different numbers produce a *conflict hint* given to the LLM, which must report both versions with sources and say if one document supersedes the other.
- **Alternative rejected:** always preferring the newest document. Without reliable dates in the files this would be a guess presented as fact; instead the system surfaces the disagreement.

## D7. Vector store: FAISS flat index with an explicit registry, not Chroma or an ANN index
- **Alternatives:** ChromaDB (built-in metadata/persistence), HNSW/IVF indexes, pgvector.
- **Choice:** `IndexFlatIP` over normalised vectors gives exact cosine search; at the target scale (thousands of chunks) it takes milliseconds, and approximate indexes only pay off beyond ~100k chunks. I keep chunk metadata and the raw vectors in my own registry so deletes are a simple rebuild, duplicates are checkable, and BM25 shares the same chunks. Persistence uses an atomic write so a crash cannot corrupt the store. The store records the embedder name and refuses to load vectors made with a different model.

## D8. Conversation context: sliding window + LLM query rewriting
- **Alternatives:** feed the whole history into retrieval; embed the concatenated history; no memory.
- **Choice:** keep the last 6 turns per session; before retrieval, a small/cheap model (Haiku) rewrites the follow-up into a standalone question, with a heuristic fallback when that call fails.
- **Evidence:** in my run the raw follow-up "And how often does it have to be changed?" scored 0.071 and was **rejected by the gate** (no relevant chunk in the top 5); its rewritten form "How often must passwords be rotated?" retrieved the right chunk. Concatenating history into the query would have worked here but pollutes retrieval when the topic changes.
